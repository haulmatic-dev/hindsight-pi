## 1. Read this first — how to not be wrong about this system

Nearly every confident number produced during this session was wrong on the first
attempt. The failures were not careless arithmetic; they were structural, and they
will happen to you too unless you follow these rules.

### 1.1 Anchor every log grep on the daemon's own prefix

Worker stdout and stderr are echoed into the same file as the daemon's log, as
`[Worker:<bead>] [stderr] {...}`. That **starts with a bracket**, so the obvious
anchor does not exclude it.

```sh
# WRONG — matches worker passthrough
grep -E '^[0-9/]+ [0-9:]+ \['

# RIGHT
grep -E '^[0-9/]+ [0-9:]+ (\[|⏸️|📊|🚀)' | grep -vE '^[0-9/]+ [0-9:]+ \[Worker:'
```

Measured consequences of getting this wrong, all today:

| Claimed | Actual | Why |
|---|---|---|
| `infra-exhausted: 473` | **0** | all 473 were inside echoed worker JSON |
| `gap_cycles: 20` (blocked a deploy) | **0** | same |
| `worker_closes: 34` | **14** | same |

**Before trusting any count, run it twice — with and without the `[Worker:`
exclusion. If they differ, the number is contaminated.** Source volume is now
reduced (pi's JSON stream is no longer promoted, `worker_spawner.go`), but old
logs and archives still contain it.

### 1.2 `grep -c` exits 1 on no match

```sh
N=$(grep -c pattern file || echo 0)   # yields "0\n0" when nothing matches
[ "$N" -eq 0 ]                        # "integer expression expected", and FALSY
```

A failing `[` is falsy, so guards written this way **silently never fire**. This
disabled the nightly matrix's own starvation guard and caused it to block a real
deploy. Pipe counts through a normaliser — see `one_int()` in
`eval/testbed-matrix.sh`.

### 1.3 Absent signals are not evidence

Twice today an absent signal was rationalised instead of investigated:

- `verdict_retained: 0` and no quarantine branches were read as "the feature is
  quiet". The truth was that a full day of deploys had been inert because
  installs went to `/usr/local/bin` while systemd runs `$HYDRA_HOME/bin`.
- A red CI check on #92 was dismissed as a flake. It was a real failure, caused by
  the change under review.

**If a feature you shipped produces no signal, prove the code ran before
concluding anything about the feature.**

### 1.4 Test through the real path, never around it

Hindsight was declared broken on MiniMax based on a raw `curl` probe showing
`<think>` tags. Hindsight strips those itself. A working configuration was
replaced with a broken one on the strength of that probe. **Exercise the code path
the system actually uses.**

### 1.5 "Deploy succeeded" and "verify-deploy OK" both mean less than they look

`verify-deploy.sh` asserts the running binary is the deployed binary. Today it
reported **OK** while the daemon ran on a configuration `deploy.sh` had just
destroyed. It says nothing about the config that binary loaded. See §3.1.

## 2. What changed today (PR #97, 12 commits)

All of it is deployed and running, none of it is yet validated by a completed
bead — see §4.1.

### 2.1 The retry cap had never fired, once, ever

`scheduler.go` cleared retry state on successful **spawn** rather than successful
**completion**, so the count could never reach 2. Across 2026-07-31 00:02–04:52
every recorded failure was `attempt 1`, `exhausted all: 0`. Beads that genuinely
could not build were retried indefinitely at ~60s intervals.

The budget is now split, per the agreed policy:

- **genuine bead faults** (exit 1, 5) consume the budget and stop at `maxRetries`
- **provider/host failures** (exit 2, 3, 4, 6, 7) pace retries via the existing
  exponential backoff but **never exhaust them**, dropping to hourly checks past
  `maxInfraRetries` (20)

An earlier diagnosis in this area was **wrong** and is corrected in task #12:
`ShouldRetry` does enforce `60s + backoff`, `RecordRetry` is called on the exit-7
path, and `worker.ID == beadIDStr`. The discarded return value was cosmetic.

### 2.2 The governor could cut concurrency but never climb back

Recovery required a full window of 8 outcomes — but a lowered limit *suppresses*
outcome volume, so a deep cut could never be undone. One provider capacity window
took the limit `4 → 2 → 1` at 02:18/02:24 and it stayed at 1 for the remaining
**2.5 hours** on a single completion.

Three fixes: `MaybeRecover()` (clock-driven from the scheduler tick, default 300s
quiet period), decrease steps down by **one** instead of halving, and **exit 7 no
longer feeds the governor** — it is a capacity blip that clears in seconds, and
feeding it in made the governor and the provider pool two controllers fighting
over one actuator.

### 2.3 Logs had no ceiling anywhere

- Daemon log: **1.56 GB in 4h50m** because `isNotableWorkerLine` promoted any line
  containing "error"/"failed"/"timeout", and pi's stream JSON carries those as
  ordinary payload. Machine events are no longer promoted; promoted lines clip at
  2 KB with a marker.
- Per-bead logs: **30 GB across 1,590 files in two days**, one bead at **853 MB**.
  Capped at 32 MB per stream, rotation now `daily` + `maxsize 64M`.

### 2.4 Tests were writing to production state

`worktreeRoot()` roots worktrees under `$HYDRA_HOME`. The daemon exports it,
workers inherit it, and when a worker ran **this repo's own test suite** every
test that created a worktree registered it in live state: **10,251 dead entries**,
each named after a Go test function, which Charon walked on every orphan sweep.
`TestMain` in `internal/core` now pins `HYDRA_HOME` to a per-run temp directory.

### 2.5 One Pi config, shared with humans

`worker_config_dir` now equals `config_dir` (`/opt/dev-tools/config/pi`), so a
skill or extension added once serves the fleet and every interactive shell. The
retired `pi-worker` copy had drifted to 239 npm packages against 242, undetected.
Both of its original purposes were obsolete. New flag `pi.manage_config`
(default **false**) stops the daemon writing to a directory humans edit.

Full detail: [`docs/architecture/pi-config.md`](../architecture/pi-config.md).
Guard: `scripts/verify-pi-config.sh`.

### 2.6 Filesystem consolidated

```

/opt/dev-tools/config/pi/          shared Pi config
/opt/dev-tools/var/hydra/          runtime state = $HYDRA_HOME
/opt/hydra                         compatibility symlink — remove after a clean run
```

`/opt/hydra` was 51 GB; it is now 1.3 GB and the disk went 68% → 56%. State is

Full detail: [`docs/architecture/filesystem-layout.md`](../architecture/filesystem-layout.md).

## 3. Traps that will bite you

### 3.1 `deploy.sh` used to destroy the live configuration

`create_config`, `create_systemd_service`, `setup_logrotate` and `setup_firewall`
wrote canned templates on **every** invocation. One ordinary deploy today:

- replaced `/etc/hydra/hydra.yaml` with a 749-byte template, losing
  `max_workers: 4`, the provider pool, the governor, `pi.*`, hindsight, phase
  models and both projects — **and the daemon started on the template**
- replaced the systemd unit with one lacking
  `EnvironmentFile=/etc/hydra/api-keys.env` (no provider credentials) and the
  beads binaries on `PATH` (`br` unresolvable)
- dropped the per-bead logrotate rule entirely

All four steps now no-op when the target exists and require `HYDRA_PROVISION=1`.
Clobbered copies are kept on the box as `*.CLOBBERED-BY-DEPLOY-20260731` next to
each restored file.

**Still missing, and worth doing first:** `verify-deploy.sh` has no config
assertion. Add one that checks the *loaded* config for expected `max_workers`,
pool size, `pi.config_dir`, `manage_config` and project count. This near-miss was
caught by luck.

### 3.2 Binary paths

systemd runs `$HYDRA_HOME/bin/hydra`. `command -v hydra` resolves to
`/usr/local/bin/hydra`, a **different file**. Installing there succeeds and
changes nothing — a full day of deploys was inert this way on 07-30. Build
packages (`./cmd/hydra`), never single files: `go build cmd/worker/main.go`
compiles `main.go` alone as `command-line-arguments` and silently ignores its
siblings, which broke the worker build today with eight `undefined:` errors.

### 3.3 Exit-code semantics

| Code | Meaning | Counts toward retry cap? | Feeds governor? | Trips breaker? |
|---|---|---|---|---|
| 1 | code failure | **yes** | no | no |
| 2 | rate limit (429) | no | **yes** | yes |
| 3 | timeout | no | **yes** | no |
| 4 | infrastructure | no | no | no |
| 5 | stub output | **yes** | no | no |
| 6 | quota exhausted | no | no | yes (30m cooldown) |
| 7 | transient overload | no | no | **no, deliberately** |

Exit 7 is `"The engine is currently overloaded"`. It burns no quota
(`usage.input=0`) and clears in seconds. Three of these inside ten minutes once
froze every spawn for fifteen minutes, which is why it is kept away from both the
breaker and the governor.

### 3.4 Never restart the daemon on top of a run

A restart kills every in-flight worker and their work is redone from scratch. On
07-30 more than ten restarts coincided with a run closing 33 beads in 21 hours
where a comparable run closed 36 in 4. `scripts/run-lock.sh` exists for this;
`eval/run.sh`, `testbed-matrix.sh` and `deploy.sh` all honour it.
